# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Bilingual (en / pt-BR) personal portfolio built on Next.js 15.5 App Router, Tailwind (class-based dark mode) and project data read from GitHub. Tests use Vitest (`@/*` alias resolved in `vitest.config.ts`).

## Commands

- `pnpm install` — install deps (`pnpm install --frozen-lockfile` in CI)
- `pnpm dev` — dev server
- `pnpm build` / `pnpm start` — production build / serve
- `pnpm lint` — `next lint` (`next/core-web-vitals`)
- `pnpm test` — `vitest run` (no network needed)
- `pnpm sync` — the owner-run Sync job (`scripts/sync.ts`, run with `tsx`, which resolves the `@/` alias): copies each Allowlisted Project's Screenshot into `public/screenshots/` (needs `GITHUB_TOKEN` once the Allowlist is not empty) generates missing Dictionary Translations and Project summary and tagline Translations (needs the Translator configured below; with an empty Allowlist the Project part prints "nothing to translate" and needs no token). `pnpm sync --regenerate-stale` also replaces Stale translations. Review with `git status` / `git diff`, then commit.

pnpm is the single package manager (pinned via `packageManager` in `package.json`); `pnpm-lock.yaml` is the only lockfile. Do not add `package-lock.json` or `yarn.lock`. `pnpm-workspace.yaml` only holds `allowBuilds` (pnpm 11 blocks dependency install scripts by default; `esbuild` and `unrs-resolver` are set to `false`).

Env vars: `GITHUB_TOKEN` (server-only, read by `lib/projects/live.ts` and `pnpm sync`; optional `GITHUB_API_URL` override, honoured by both), `REVALIDATE_KEY` (checked by the revalidate route). Translator env vars (read only by `pnpm sync`, never by the site; put them in `.env.local`, which `pnpm sync` loads (`tsx --env-file-if-exists=.env.local`) and Next loads for dev/build/start; `.env.local` is git-ignored): `TRANSLATOR` (`gemini` default, or `libretranslate`), `GEMINI_API_KEY` (never committed; a free key from Google AI Studio), `GEMINI_MODEL` (default `gemini-3.5-flash-lite`), `LIBRETRANSLATE_URL` (default `http://localhost:5000`), `LIBRETRANSLATE_API_KEY` (optional). `.env.example` lists every variable; copy it to `.env.local`. No real `.env*` file is committed.

## Architecture

**Locale module (`lib/locale/`).** The only place that knows the Locales. It exports `locales`, `Locale`, `defaultLocale`, `isLocale`, `negotiateLocale(acceptLanguage)` (q-values, underscores, case-insensitive, regional tags match their language, unknown gives the default), `hasLocalePrefix(path)`, `localePath(locale, path)` (absolute path for an unprefixed path), `stripLocalePrefix(path)` (the path without its Locale prefix; the Locale root gives `/`), `switchLocalePath(path, locale)` (prefixed or unprefixed input), `localeNames` (`Record<Locale, string>` of native names, "English" / "Português", kept out of the Dictionary so they read the same in every Locale) and `getDictionary(locale)` (English for an unknown Locale). It is pure and unit-tested in `lib/locale/locale.test.ts`. Middleware, the root layout, `NavBar`, `LocaleSwitch`, `ProjectIndex` and the pages all go through it; nothing else hard-codes `en` or `pt-BR` (apart from the file names and registry keys in `dictionary/`). Every link is built with `localePath`, never a relative href. Adding a locale means adding it to `locales` and `localeNames` (typed, so TypeScript flags a missing name) and running `pnpm sync`, which creates `dictionary/<locale>.ts` and adds it to `dictionaries` in `dictionary/index.ts` (typed `Record<Locale, DictionaryEntry>`, so TypeScript flags a missing one). See "Try a new Locale end to end" below.

**Locale routing via middleware.** All pages live under `app/[lang]/`. `middleware.ts` checks `hasLocalePrefix(pathname)`; if the path is not prefixed, it uses `negotiateLocale` on `Accept-Language` and *rewrites* (not redirects) to `localePath(locale, pathname)`. So the URL bar stays locale-free until `LocaleSwitch` (a native `<select>` listing every Locale from `locales` by `localeNames`, labelled by `NavBar.Language`, each `<option>` with its `lang`) pushes an explicit `/{lang}/...` path. `config.matcher` in `middleware.ts` exempts `_next`, `api`, `favicon.ico` and static file extensions (png, jpe?g, gif, webp, svg, ico, pdf, txt, xml) from the rewrite, so assets such as `/screenshots/x.png` and `/cv/en.pdf` and the `/api/revalidate` route are served as they are. The route segment is `[lang]` and Next types route params as `string`, so each page and the layout reads it once as `const locale = (await params).lang as Locale` (the middleware guarantees a valid prefix); from there on, props and variables are called `locale` and typed `Locale` (`NavBar`, `ProfileLinks`, `LocaleSwitch`, `ThemeSwitch`, `ProjectIndex`). Because those paths stay unprefixed, an unknown file such as `/old-name.pdf` matches `[lang]`, so `app/[lang]/layout.tsx` calls `notFound()` when `isLocale(lang)` is false (404 instead of a rendered page). Do not use `export const dynamicParams = false` for that: with it, `POST /api/revalidate` makes every revalidated page answer 404 (`NoFallbackError`, Next 15.5.28) until the next deploy; found and fixed during ticket 16 (a production build with a revalidate reproduced it at the previous commit).

**The Dictionary is typed from English.** `dictionary/en.ts` is the hand-edited Source text: `export const en = {...}` and `export type DictionaryEntry = typeof en` (string leaves are plain `string`), the single definition of the shape. Other Locales are separate files (`dictionary/pt-BR.ts`) typed `DictionaryEntry`, so a missing or extra key is a compile error; `dictionary/index.ts` exports `dictionaries: Record<Locale, DictionaryEntry>`, which `getDictionary` reads. `dictionary/dictionary.test.ts` also fails if any Locale's nested key paths differ from English. Pages read `const dictionary = getDictionary(locale)` and then `dictionary.Section.Key`. Every user-visible string lives here (page `<title>`/description come from `Meta` via `generateMetadata` in `app/[lang]/layout.tsx`); a new string goes in `en.ts` and every other Locale file. Still hard-coded on purpose: the owner's name and the LinkedIn/GitHub link names (in `lib/profile-links.ts`). `app/[lang]/not-found.tsx` (client component, Locale from `useParams`) is the translated missing-Project state; `notFound()` gives status 404, but the text only appears after hydration (the server HTML is an empty client-render shell, as it was with the default 404).

**Project data comes from GitHub through `lib/projects/` (server components).** The Allowlist is `projects.allowlist.ts`; the live adapter is `lib/projects/live.ts` (see ADR 0001), and the pages read through the module in `lib/projects/index.ts`. The build fails loudly on a bad or missing token or an unreadable Allowlisted repo.
- `projects/page.tsx` is a server component: it lists Projects through the module and passes `{ slug, title, tagline }` (the Tagline is already resolved for the Locale), the Locale and `dictionary.Projects` (as `labels`) to `components/ProjectIndex.tsx`. No Screenshots on this page.
- `ProjectIndex` (client component) renders the whole listing: mono breadcrumb, giant title with a `(NN)` count (visible part `aria-hidden`, `sr-only` text is `Projects.CountLabel` plus the number), intro, the PROJECT INDEX / EXPLORE THE WORK row, one row per Project in Allowlist order (zero-padded index, title, circle arrow, rules) and a bottom bar with "Back to top" (`window.scrollTo` to the top). Each row is one `next/link` with `localePath(locale, "/projects/" + encodeURIComponent(slug))`. The active row (`useState` of the active slug; mouse enter/leave and focus/blur on the links) shows its Tagline (none when the Project has none), the "View project" label (`md` and up) and a filled circle. Nothing queries the document; nothing needed to use the page is hover-only. The pure parts (`padNumber`, `indexLabel`, `rowState`, `deactivate`) live in `lib/project-index.ts` and are tested in `lib/project-index.test.ts` (Vitest runs in `node`, there is no DOM test setup). The listing strings are the `Projects.*` keys (`Breadcrumb`, `Intro`, `IndexLabel`, `Explore`, `ViewProject`, `FooterBreadcrumb`, `BackToTop`).
- The typographic cover (ticket new-layout/05) is what a Project without a Screenshot shows on its page; there is no placeholder image any more (`SCREENSHOT_PLACEHOLDER` and `public/screenshot-placeholder.svg` were removed). The pure part is `lib/projects/cover.ts` (tested in `cover.test.ts`): `splitTitle` (first word / rest, splitting at whitespace and underscores), `coverLabels` (top: title and `NN–NN` position; bottom: first two topics joined with ` / `, third topic; `null` without topics) and `fitScale` (font-size factor 0.3 to 1 for long words).
- `projects/[projectName]/page.tsx` (`ProjectPage`, ticket new-layout/04) is a server component. It lists Projects through the module (`listProjects(locale)`, Allowlist order) and calls `projectNavigation(slugs, slug)` (`lib/projects/navigation.ts`, pure, tested in `navigation.test.ts`): `{ position (1-based), total, next }` where `next` wraps from the last Project to the first and is `null` with a single Project (then the "Continue exploring" row is omitted); `null` for an unknown slug gives `notFound()` (rendered by `app/[lang]/not-found.tsx`). Layout: back link and mono "PROJECT 01 / 04", huge title with the tagline at the right (omitted when `null`), then two columns (stacked below `md`): "01 Project summary" (with the Code / Visit buttons only when `codeUrl` / `demoUrl` exist) and "02 Project Stack" (topics as bordered `font-mono` chips, section omitted without topics), and the cover slot on the right; then "Continue exploring" with "NEXT / NN title", and a bottom bar "PROJECTS / title" and "All projects". The strings are in the Dictionary under `Project` (plus `ProjectInfo` for the section headings and buttons). The cover slot is `components/ProjectCover.tsx` (`title`, `screenshot: string | null`, `label`): takes `title`, `screenshot: string | null`, `label`, `position`, `total`, `topics`. With a Screenshot it shows it in a bordered frame; without one it renders the typographic cover (grid, mono corner labels from `coverLabels`, big first word, smaller rest, arrow; sizes in `cqw` container-query units of the panel so it never overflows or depends on the viewport; the whole figure is `aria-hidden` because the title is already the h1). Both have the mono caption row (title, `Project.CoverLabel`) under them. No new per-Project fields.
- The Allowlist is deduplicated by repo (first entry wins) with `dedupeAllowlist` from `lib/projects/allowlist.ts`, used by both `createProjects` and `runSync`.
- A Project's summary comes from the README's Marked block, `<!-- portfolio:start -->` ... `<!-- portfolio:end -->` (`lib/projects/marked-block.ts`); see the README for the syntax. Without a usable block the summary is the repo's short GitHub description. Fallback chain (`resolveSummary` in `lib/projects/index.ts`): a stored Translation for the requested non-default Locale whose `sourceHash` equals `hashSourceText(live Marked block)` and whose text is not blank; else the live English Marked block (always the case for the default Locale, which has no entries); else the short description.
- A Project's **tagline** (`Project.tagline: string | null`, ticket new-layout/02) is the repo's short GitHub description, trimmed (`taglineSourceText` in `lib/projects/tagline.ts`, shared by the Projects module and Sync so both hash the same text). `null` when the repo has no description or it is blank. Same chain as the summary (`resolveTagline` in `lib/projects/index.ts`): a stored tagline Translation for the requested non-default Locale whose `sourceHash` equals `hashSourceText(trimmed description)` and whose text is not blank; else the live English description (always the case for the default Locale). The description arrives through the same tagged repo-metadata fetch as everything else, so `POST /api/revalidate` refreshes it in every Locale like the summary. The listing and Project pages that show it come in tickets 03 and 04.
- Project summary and tagline Translations are read by `createTranslationReader` (`lib/projects/translations.ts`; `getTranslation` for the summary, `getTaglineTranslation` for the tagline) from the committed `projects.translations.json` (repo root), `{ "<repo>": { "<locale>": { "text"?: string, "sourceHash"?: string, "tagline"?: { "text": string, "sourceHash": string } } } }`: `text` + `sourceHash` are the summary (unchanged since ticket 16), `tagline` is optional and independent of them (old-shape entries without it stay valid; a repo with a description but no Marked block has only `tagline`), **imported statically** so it is part of the build and works under any host (no request-time filesystem access). A pair without both strings counts as no Translation; a file that is not a JSON object fails the build. A changed file shows after the next deploy; GitHub changes show after the revalidate route.

**GitHub requests (`lib/github/request.ts`).** `lib/projects/github.ts` and `lib/sync/github-screenshots.ts` both go through `githubFetch` (Bearer token, `X-GitHub-Api-Version` header, missing-token error, "cannot reach GitHub" error) and `assertReadable` (401/403 means the token was rejected, except that a 403 with `x-ratelimit-remaining: 0` or `retry-after`, or a 429, says the rate limit was reached; other non-404 errors name the status). `DEFAULT_API_URL` lives there too. The token never appears in a message; the Sync adapter also leaves out the low-level network error text (`includeReason` off).

**Sync job (`lib/sync/`).** `runSync({ github, store, allowlist })` returns `{ screenshots: { copied, unchanged, skipped, failed } }` (repo names; `failed` entries carry `{ repo, error }`). `github` is a `ScreenshotSource` (`getScreenshot(repo)` gives bytes or null) and `store` a `FileStore` (`read`/`write` by public path). It only touches Allowlisted repos, so a Hidden repo's image is never fetched or copied. The fixed Screenshot path in each Project's repo is **`docs/screenshot.png`** (`SCREENSHOT_REPO_PATH` in `lib/sync/github-screenshots.ts`; must be a PNG). It is written to `public/screenshots/<repo>.png`; the name always comes from `screenshotPath` in `lib/projects`, the same function `screenshotExists` uses to decide whether the site shows it or the typographic cover. Identical bytes are not rewritten (compared by content), a repo without the file is skipped and reported, and one repo's failure (for example a 403) does not stop the others; `pnpm sync` exits 1 if any failed. Error messages never include the token. Real adapters: `createGitHubScreenshots` (contents API, `Accept: application/vnd.github.raw+json`, no Next fetch cache) and `createFileStore` (rooted at `public/`); `createMemoryStore` is for tests. The optional `translations` dependency adds the Dictionary step and a `translations` key on the report (below). The steps are isolated: if one rejects outright, `runSync` records it as a failure under that step's own report key (entry `(step)`: `screenshots.failed`, a `"(step)"` key in `translations`, `projectTranslations.failed`) and the others still run and keep their reports; `pnpm sync` exits 1 if any repo, Dictionary entry or Project summary failed, and prints the failure. Everything printed, including the top-level crash message, goes through `createRedact` (`lib/sync/redact.ts`) with the token and API keys.

**Translator (`lib/translator/`) and Dictionary Translations (ticket 15, ADR 0002).**
- `Translator` is `translate(text: string, locale: string): Promise<string>`; the source language is always English (`SOURCE_LANGUAGE`). `createTranslator(env, fetch?)` picks the adapter from `TRANSLATOR`; an unknown value is a `TranslatorConfigError`. `fetch` is injected, so tests never touch the network; `createFakeTranslator` (`fake.ts`) is the test double.
- Gemini adapter (`gemini.ts`): REST `POST /v1beta/models/<model>:generateContent`, no SDK, key in the `x-goog-api-key` header (never in a URL or an error message), `temperature: 0`. The system prompt says: translate only, reply with only the translation, keep product names, code, URLs and placeholders, add no commentary. The language name comes from `Intl.DisplayNames` (`languageName`), so no per-Locale table exists. A missing `GEMINI_API_KEY` is a clear error on the first `translate` (not at construction, so a run with nothing to translate does not need it). 429/503 are retried up to 3 attempts, waiting for `Retry-After`/`retryDelay`. The default model is `gemini-3.5-flash-lite`, which Google's pricing page lists as free of charge on the Free Tier and recommends for new projects (checked 2026-10-29); override with `GEMINI_MODEL` if Google renames or retires it. It has never been run against the real API (no key exists here).
- LibreTranslate adapter (`libretranslate.ts`): `POST <url>/translate` with `format: "text"`; sends the primary subtag (`pt-BR` as `pt`).
- Source hashes live in the committed **`dictionary/.sync-state.json`**: `{ "<locale>": { "<Section.Key>": "<sha256 of the English text the Translation was made from>" } }`, keys sorted, written only when it changes. Hash function: `hashSourceText` (`lib/projects/hash.ts`, node-only; Sync is the only importer of it besides the server-side Projects module).
- `syncTranslations` (`lib/sync/translations.ts`), per target Locale (the `locales` list minus English): an entry with no Translation (every entry, when the Locale has no file) is translated and its hash recorded. An entry with a Translation and no recorded hash is **baselined**: the current English hash is recorded and nothing is sent or changed (this is how the hand-written `pt-BR.ts`, including its owner-set `About.Text`, is protected). An entry whose recorded hash differs from the current English is **Stale**: reported on every run, left alone, and replaced only with `--regenerate-stale` (which applies to every Locale). Entries whose hash matches are never sent. Per Locale it is all or nothing: if any Translator call fails, nothing of that Locale is written (file, state or registry), the failed entries are reported, and the other Locales still run. A file Sync cannot parse, a state file that cannot be read or is corrupt, or an invalid Locale tag is reported as a failure (`(file)` or `(state)`) and left alone. Write order: plan every Locale (no writes), write the state, write the Locale files, and write the state again only if something was regenerated. The first state write holds every hash that is safe before its text exists (a hash without a Translation just gets translated again) but keeps the old hash of regenerated entries; the second bumps those only after their Locale file was written. So a failed write leaves entries Stale or untranslated, never wrongly fresh; if the state cannot be written, no Locale file is written.
- File format (`lib/sync/dictionary-file.ts`): exactly the shape of `pt-BR.ts` (`import type { DictionaryEntry } from "./en"`, `export const <camelCaseLocale>: DictionaryEntry = {...}`, 4-space indent, English key order, double-quoted strings, no trailing commas). Sync reads files with a small parser for that subset (plain nested objects of string literals; comments, single quotes and trailing commas are tolerated, templates and expressions are not) and only rewrites an existing file when it is already byte-identical to what Sync would render for its current content; otherwise it refuses and lists the keys to add by hand, so it never reformats the owner's file or drops a comment. Existing values are never altered except by `--regenerate-stale`.
- Registry: Sync patches `dictionary/index.ts` itself (an import after the last import and an entry at the end of `dictionaries`). If the file no longer has that shape it prints the exact two lines to add (`registry: "manual"`). `Record<Locale, DictionaryEntry>` still makes a missing entry a compile error.
- `localeNames` cannot be generated (it is the Locale's name in its own language): the script prints a REQUIRED line when a Locale in `locales` has no name.

**Project summary and tagline Translations (tickets 16 and new-layout/02, `lib/sync/project-translations.ts`).** `runSync({ ..., projectTranslations })` (`ProjectTranslationsDeps`: `translator`, `readmes: ReadmeSource`, `descriptions: DescriptionSource`, `store` rooted at the repo root, `sourceLocale`, `locales`, `regenerateStale`) returns a `projectTranslations` report `{ generated, regenerated, stale, unchanged, skipped, taglines, pruned, failed }`: the first five keys are about summaries, `taglines` is `{ generated, regenerated, stale, unchanged, skipped }` for taglines, `pruned` and `failed` cover both (`ProjectTranslationRef` is `{ repo, locale }`; `stale` entries add `unknownHash`; a `failed` entry about a tagline has `field: "tagline"`). Real README adapter: `createGitHubReadmes` (`lib/sync/github-readmes.ts`, `githubFetch` + `assertReadable`, readme API with `Accept: application/vnd.github.raw+json`, no Next cache; a README 404 is checked against the repo endpoint, because GitHub also answers 404 for a private repo the token cannot see: repo 404 too means the read rejects with a clear error and is reported as failed, repo readable means "no README", `null`, skipped); `createGitHubDescriptions` (`lib/sync/github-descriptions.ts`, repo metadata, no Next cache, a 404 rejects for the same reason, a missing or blank description is `null`) reads the tagline Source text; `formatProjectTranslationsReport` prints both, under "Project summaries" and "Project taglines".
- Only Allowlisted repos (deduplicated) are read, so Hidden repos are never fetched or sent to the Translator. For each, `extractMarkedBlock` of the README gives the Source text; no block means the repo is `skipped` and reported (its summary is not translated and existing summary entries are left alone). For each non-default Locale: no entry or blank text means translate and record `hashSourceText(block)`; `sourceHash` equal means unchanged (never sent); different or missing hash means stale (a missing hash is `unknownHash`: there is no baselining here because no hand-written summaries exist), left alone unless `--regenerate-stale`. Entries are never overwritten otherwise, and the default Locale is ignored.
- Taglines go through the same flow, on their own: the Source text is the trimmed short description of each Allowlisted repo (read through `descriptions`, so Hidden repos' descriptions are never fetched or sent either); no description means the repo is in `taglines.skipped` and its existing tagline entries are left alone; no `tagline` or blank text means translate and record `hashSourceText(description)`; equal hash is unchanged; different or missing hash is stale (left alone unless `--regenerate-stale`). The two fields of an entry never affect each other: writing one keeps the other (and any unknown key) as it was, and a repo can have one without the other. Entries are written in the order `text`, `sourceHash`, `tagline`.
- Two phases: read and classify every README and description, then translate. Any failure (a README or description that cannot be read, a Translator error or empty answer, a file that is not valid JSON or has the wrong shape, an invalid Locale tag) means nothing is translated or written and `failed` names the entries (`repo` is `(file)` or `(locale)` for whole-file problems). The file is rewritten only when something (summary or tagline) was generated or regenerated, with sorted keys, two-space indent and a final newline. Entries for repos not on the Allowlist are **pruned** from the file (a Hidden repo's name must not stay in committed data) and listed as `pruned` so the owner sees it in the diff; pruning is part of the all-or-nothing write, so a failed run prunes nothing, and it also happens when the Allowlist is empty (which otherwise reads no README and translates nothing). Sync does not delete files in `public/screenshots/`; a removed repo's old Screenshot stays until deleted by hand.
- `pnpm sync` exits 1 on any failure in any step (Screenshots, Dictionary, Project summaries and taglines).
- Verified end to end on 2026-10-29 (no real Gemini; fake LibreTranslate HTTP server and a fake GitHub API via `GITHUB_API_URL`, temporary Allowlist entry, then reverted): Sync generated the `pt-BR` entry, a second run sent nothing, the production build showed it on `/pt-BR/projects/<slug>` and English on `/en/...`, then after the fake README block changed and `POST /api/revalidate` both Locales showed the new English text (stale => fresh English); `--regenerate-stale` replaced it; with the Translator unreachable the run exited 1 and left the file untouched.

**Try a new Locale end to end.** Example `es`:
1. Add `"es"` to `locales` in `lib/locale/index.ts`.
2. Add `es: "Español"` to `localeNames` in the same file (its name in its own language).
3. Run `pnpm sync` with a Translator configured (`GEMINI_API_KEY=... pnpm sync`, or `TRANSLATOR=libretranslate pnpm sync` against a local server). It creates `dictionary/es.ts`, patches `dictionary/index.ts`, and records the hashes in `dictionary/.sync-state.json`.
4. Review `git diff` / `git status` (read the machine translation; edit any wording, edits are never overwritten), then `pnpm test`, `pnpm exec tsc --noEmit` and commit.
5. Two things outside Sync: the CV (`public/cv/es.pdf`, and `cvLocales` in `lib/profile-links.ts`, otherwise `cvPath` falls back to English and its test, which expects one file per Locale, fails; a test also checks every listed Locale is a known Locale with its file on disk, and the download name follows the Locale of the file actually served), and the revalidate route test, which spells out the Locale list.
Verified end to end on 2026-10-29 with a throwaway `es` against a fake LibreTranslate server: parity test and `tsc` passed, and the Locale was then reverted.

**Cache invalidation.** Every GitHub fetch in `lib/projects/github.ts` carries `next: { revalidate: 3600, tags: ["projects"] }`. `POST /api/revalidate` (key in the `x-revalidate-key` header, compared in constant time with `REVALIDATE_KEY`; 401 if missing, wrong, or `REVALIDATE_KEY` is unset) calls `revalidateTag("projects")` and `revalidatePath` for each concrete `/{locale}/projects` and `/{locale}/projects/{slug}` (locales from `lib/locale`, slugs from `listSlugs()`). Do not pass `"/[lang]/projects"` to `revalidatePath`: a dynamic pattern without a `type` has no effect. The old header name `revalidate_key` is still accepted but deprecated (the underscore is dropped by nginx by default); new callers use `x-revalidate-key`.

**Profile links (`lib/profile-links.ts` + `components/ProfileLinks.tsx`).** The only place the LinkedIn, GitHub and CV URLs (CV = `public/cv/<locale>.pdf` via `cvPath(locale)`, falling back to the default Locale's file, rendered with `download`) are written. `<ProfileLinks variant="icons" | "labelled" locale={locale} />`: `icons` is Home (icon-only links named by `aria-label`), `labelled` is About (icon plus text). SVGs are `aria-hidden`. The rule for each link's accessible name (`profileLinkName`: the CV name is `About.CVDownload` from the Dictionary, LinkedIn/GitHub names are constants in the links file) and for its anchor attributes (`profileLinkAnchorProps`: external links get `target="_blank" rel="noopener"`, the CV gets `download`) lives next to the data in `lib/profile-links.ts`, so the component does not branch on the link. To change a URL, edit the links file only.

**Header and page column.** `components/NavBar.tsx` (client) renders Home / Projects / About with the active link marked (`aria-current="page"`, full-brightness text and a short underline), a divider under the bar, then `LocaleSwitch`, a thin separator and `ThemeSwitch`. The active item comes from `activeNavItem(pathname)` in `lib/nav.ts` (pure, tested in `lib/nav.test.ts`; Projects stays active on a Project page, in any Locale). `app/[lang]/layout.tsx` wraps header and page in one centered column (`mx-auto w-full max-w-[1400px] px-5 md:px-10 lg:px-16`). It also loads IBM Plex Mono through `next/font` and exposes it as the CSS variable `--font-mono`, which Tailwind's `font-mono` uses (`tailwind.config.js`); use `font-mono` for labels (breadcrumbs, counts, chips).

**Theming.** `components/Theme.tsx` wraps `next-themes` (`attribute="class"`) and pairs with Tailwind `darkMode: 'class'`; `ThemeSwitch` toggles it.

**Config notes.** `next.config.js` is empty: all images are local (`public/`), so no `next/image` host allowance is needed. `@/*` maps to the repo root (no `src/`). `public/cv/<locale>.pdf` are the CVs (one per Locale) linked from the Home and About pages.

## Agent skills

### Issue tracker

Local markdown under `.scratch/<feature>/`. See `docs/agents/issue-tracker.md`.

### Triage labels

Default five-role vocabulary (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`). See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: one root `GLOSSARY.md` plus `docs/adr/`. See `docs/agents/domain.md`.
